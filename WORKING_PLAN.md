# Working Plan

This document explains how the project is organized and how the work is planned.

## Goal

`md-to-anything` is a CLI for turning Markdown into PDF, DOCX, or HTML output with clean templates and a simple release flow.

## How the project is made

The project follows a straightforward pipeline:

1. `src/cli.ts` reads the command-line arguments.
2. `src/parser.ts` loads Markdown and frontmatter from disk.
3. `src/template.ts` renders the selected HTML template.
4. `src/converters/` turns the parsed document into HTML, PDF, or DOCX.
5. `src/batch.ts` handles glob-based multi-file conversion.
6. `src/preview.ts` powers live preview and hot reload.
7. `src/logger.ts` prints user-facing status messages.
8. `tsup.config.ts` bundles the CLI for release.

## Planned workflow

The planned work is organized into short, release-friendly steps:

### Phase 1: Core CLI

- Parse input file arguments
- Support `--format`, `--template`, `--output`, `--watch`, and `--port`
- Keep the CLI output clear and predictable

### Phase 2: Rendering and conversion

- Parse Markdown into HTML
- Render built-in and custom templates
- Convert HTML to PDF and DOCX

### Phase 3: Batch and preview features

- Convert many Markdown files with `batch`
- Keep live preview working with file changes
- Maintain consistent logging for success and failure cases

### Phase 4: Documentation and release packaging

- Keep the README aligned with the CLI
- Maintain the file structure reference
- Keep build tooling ready for npm publishing

### Phase 5: Testing and quality checks

- Keep parser behavior covered by tests
- Verify build output before release
- Keep generated files out of source control when possible

## Current project structure

- `src/` contains the runtime code.
- `templates/` contains built-in HTML templates.
- `examples/` contains sample Markdown input files.
- `tests/` contains the parser test suite and fixtures.
- `dist/` is generated by the build.

## Near-term milestones

1. Keep the CLI build stable with `tsup`.
2. Keep parser tests passing.
3. Keep the README and file structure documentation current.
4. Prepare the repository for release and publishing.

## Notes

- This plan is intentionally short so it can be updated as the project grows.
- If a new feature changes the pipeline, update this file first and then update the implementation docs.
